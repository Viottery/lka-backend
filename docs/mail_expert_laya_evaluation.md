# 邮件专家意图路由：LayA 与 LLM 对照（2026-09-30）

## 方法

固定的 27 条合成英文/中文请求，六个标签 `search/list/review/group_sender/align_matter/unsupported`；每个标签 4 条，`unsupported` 7 条。请求不含真实邮箱内容。脚本为 `scripts/benchmark_mail_expert_routes.py`，样本为 `evals/fixtures/decision_models/mail_expert_routes.jsonl`。测量的是**模式分类**，不测时区区间抽取、工具授权、事项匹配准确率，也不是端到端 Agent 成功率。

LayA：`convaiinnovations/laya-multilingual`，CPU、8 线程，单进程热模型顺序推理；首次加载时间单独测。LLM：项目当前配置的 PackyAPI `deepseek-flash`，JSON 格式，输出预算 300 token，顺序远程调用。两个模型使用各自的分类提示，因此这是应用方案对照，不是完全相同提示词的架构消融。先前 40-token LLM 试跑因推理 token 用尽返回空正文，已废弃，以下只采用 300-token 正式运行。原始逐例本地报告在 `/tmp/lka-mail-laya-report.json`、`/tmp/lka-mail-llm-report.json`，不纳入版本库。

| 指标 | LayA | LLM JSON |
| --- | ---: | ---: |
| 正确/总数 | 15/27 | 25/27 |
| 准确率 | 55.56% | 92.59% |
| 单次 p50 | 107.46 ms | 1442.50 ms |
| 单次 p95 | 123.58 ms | 2091.01 ms |
| 无法解析输出 | 0 | 2 |
| 已记录远程 token | 0 | 5173（仅成功解析的 25 次，非总消耗） |
| 冷加载 | 16183.96 ms | 未测连接/服务冷启动 |

LayA 进程峰值 RSS 从加载前约 183 MiB 到加载后约 2569 MiB；这是进程峰值，非精确模型独占内存。LayA 本地调用无远程 token 计费，但有 CPU 与常驻内存成本。LLM 的两个空 JSON 结果没有被脚本计入 token 汇总，因此 5173 是**下界**，不能拿来精确计算每成功路由的实际费用；现金费用还取决于服务定价和缓存命中，本次未换算。

| 标签 | LayA | LLM |
| --- | ---: | ---: |
| search | 2/4 | 4/4 |
| list | 3/4 | 4/4 |
| review | 1/4 | 4/4 |
| group_sender | 1/4 | 4/4 |
| align_matter | 1/4 | 3/4 |
| unsupported | 7/7 | 6/7 |

LayA 对 7 条不支持/写请求均选了 `unsupported`；LLM 未解析的一条模糊请求算失败，但没有错误放行写操作。LayA 将多条中文发件人整理误归到 `search/list`，将事项对齐误归到 `list/unsupported`。这个六路任务上，较低耗时不能抵消错误工作流选择风险。样本数小且人工合成，结果只支持当前配置下的方向性判断，没有统计置信度或真实流量代表性。

## 使用决策

线上邮件专家意图识别**继续用 LLM JSON 路由**，不让 LayA 独占、自动执行或扩大权限。LayA 可在单独的影子实验中做低风险候选提示；但接入前至少需要：(1) 扩充真实匿名化且按任务/语言分层的标注集，保留独立 holdout；(2) 对双语候选描述、候选层级和拒识阈值只在 dev 集调参，在 holdout 检验；(3) 逐项记录选择、候选分数、延迟、回退次数与误路由代价；(4) 只有在安全类误放行为零且各高价值类别达到预定门槛时，才考虑 `LayA 预选 → LLM 复核/回退`。分数未经校准，不可直接解释为正确概率。写操作仍需正常 Tool Executor 安全审查，LayA 不参与授权。

本次没有启用线上 LayA：它要求额外依赖和约 2.5 GiB 的进程峰值内存，在当前样本的 `group_sender/align_matter` 上各只有 1/4 正确。即使顺序执行时热推理明显快，若大量请求回退 LLM，总延迟还可能高于纯 LLM；必须另测影子流量的实际回退率。

## 后续实验：双语、多维与窄候选（2026-10-01）

复现脚本：`scripts/experiment_mail_laya_routes.py`。在原 27 条开发集之外，新建 24 条中英挑战样本（六类各 4 条）和 12 条交叉措辞压力样本；样本均为人工合成，不含真实邮件。LayA 仍使用同一多语言 checkpoint、CPU 8 线程。挑战集 LLM 用原配置重新调用，正确 22/24，p50 1332.97 ms，记录 5490 token；其中一条模型输出无法解析，另一条模糊请求被误选为 `review`。不同运行间延迟不能视为严格同条件基准。

| 方法 | 原开发集 | 新挑战集 | 挑战集热推理 p50 |
| --- | ---: | ---: | ---: |
| LayA：原英文六选一 | 15/27 | 未在新集运行 | 原运行 107 ms |
| LayA：互斥双语说明六选一 | 17/27 | 14/24 | 174 ms |
| LayA：一次调用回答安全/目标/整理维度，规则合成 | 11/27 | 7/24 | 265 ms |
| LLM JSON | 25/27 | 22/24 | 1333 ms |

多维方案的三个问题确实由一次 `predict` 调用，但问题更多、耗时更高；实际输出常把只读请求判为写操作或目标不明。不能把“模型支持多问题”推断成“拆问题一定提高准确率”。双语说明相对原开发集略好，但挑战集仍不及 LLM。

**高分差选择性回退**：预先固定规则为 LayA 双语六选一的非 `unsupported` 结果且前两项概率差至少 0.9 时直通，其余复用逐例 LLM 结果。挑战集有 8/24 条直通，模拟正确率从纯 LLM 的 22/24 降为 21/24，已记录 LLM token 从 5490 降至 3804（减少约 31%），离线相加的 p50 从 1333 ms 升至 1472 ms。原开发集仅 1/27 条直通，已记录 token 从至少 5173 降至至少 4993，p50 从 1443 ms 升至约 1608 ms。此处的耗时是分别实测后相加的**重放估计**，不是实际混合流水线或并发运行测量；开发集两个 LLM 空输出的 token 仍缺失。挑战集直通的两条错误分别是 `list→search` 和 `review→search`。模型曾以 0.98 以上的前两项概率差给出错误标签，原始分差不能当可靠的直通保证。

**窄候选探针**：假定上游已正确判定“这是整理任务”，仅让 LayA 在发件人分组与已有事项对齐之间二选一，原开发集 8/8、新挑战集 8/8，热推理 p50 约 88–92 ms。但随后专门设计的 12 条交叉措辞压力样本只有 6/12，且部分错误分差超过 0.87。这个二选一没有解决上游“是否整理”的判断，也没有展示可靠拒识能力。压力集是在看到前两组结果后编写的反例，不应当作独立 holdout，却足以反驳直接上线的判断。

**结论**：目前三种“更聪明”的零样本 LayA 用法都未在挑战样本上同时达到现有 LLM 的准确率与延迟优势。继续保留 LLM 意图识别，不增加 LayA 到在线必经路径。下一步若仍要探索，优先收集匿名化真实请求、做明确的上游候选构造与独立验证；或在足量标注数据上评估针对邮件任务的轻量分类器/微调，而不是继续凭同一小样本调阈值。任何直通策略须用真实分布证明总体质量、错误代价、回退率、端到端耗时及内存收益。
