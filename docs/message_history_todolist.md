# 跨平台只读消息历史与自动分析 TODO

本轮目标（2026-10-04）：在现有 Windows QQ Reader 基础上，打通“白名单消息 →
可靠同步 → 本地历史 → 有来源的摘要/信息提取 → Agent 只读查询”。不接入 QQ 写操作，
初版使用合成数据验证，不自动创建事项或写入个人长期记忆。后续用户明确授权的
Windows 实机采集和本地媒体缓存单列在下方，不扩大到其他会话。

本文件的已完成项仅代表第一阶段历史／摘要基础链路。后续“大群阅读与防遗漏”完整规格见
[跨平台消息阅读后台服务设计](message_reading_service_design.md)，新增阶段的实现状态见文末。

## 实施顺序与验收

1. [x] 通用协议和历史仓库：平台/账户/会话隔离，消息幂等；发送、接收、入库三个时间；
   会话内递增序号；原文保留；非文本仅记录不可解析标记。
2. [x] 后端权威白名单：记录/分析独立开关、默认批量 20、revision CAS；撤销后停止导入、
   分析和 Agent 读取，不删除历史。采集端仅缓存已确认策略，不默认记录所有聊天。
3. [x] 本地同步合同：通用导入及 QQ v1 兼容；导入专用 token，不授权读取正文或修改策略；
   仅提交成功后 ack；逐条永久拒绝与临时重试分开，坏消息不堵塞后续队列。
4. [x] 自动分析：每满 N 条唯一消息形成固定序号批次，同会话串行、不同会话有界并发；
   后台共享队列按注册 kind 领取；失败保留旧摘要/游标，支持手动处理尾批和重试。
5. [x] 可追溯发布：批次摘要、滚动摘要、结构化信息及原消息引用；校验引用；按租约与
   策略版本原子发布；明确 inbound_only、覆盖水位和未处理原文，不将推测当作事实。
6. [x] Agent 接入：messages.list_conversations/recent/search/history/summary/facts 全部只读；动态白名单与
   child 的 source/account scope 双重过滤，无原始 OneBot client、无后台分析写工具。
7. [x] 前端采集适配：QQ 与 Mock 共用规范；白名单前置、离线策略缓存、断线恢复、
   幂等 ack/拒绝隔离；不迁移或删除既有消息。前端 UI 可配置白名单、浏览历史/摘要、
   查看覆盖及触发尾批处理/失败重试；沿用当前页面，不引入 React。
8. [x] 针对性验证与独立审查：合成消息覆盖去重、阈值、隔离、乱序、撤销、失败重试、
   租约失效、来源校验；不运行全量测试或大规模 benchmark。

依赖：1/2 定义合同后，后端分析与前端采集可以并行；3/5/6/7 集成后再做 8。

## 固定边界

- QQ 连接仍在 Windows 前端本地服务，不进浏览器，不改变现有 QQ/NapCat/SnowLuma 安装。
- 通用消息字段：platform/account_id/message_id/conversation_type/conversation_id/
  sender_id/sender_name/text/sent_at/received_at/content_kind；后端生成 ingested_at、seq、
  conversation_key/source_id/account_scope_id。身份不以昵称或时间戳作为去重依据。
- sent_at 无效时为 null，并标注时间质量；处理水位按 seq，不因迟到消息跳过分析。
- 未进入白名单不持久化正文；不主动查询联系人，不导入历史库。
  后续获批的图片/视频扩展仅在单独启用 media_enabled 的白名单会话下载。
- 摘要与事实是可重建派生数据，不替代原文；聊天文本始终是不可信数据，不能触发工具。
- 本地控制 API 与导入 API 分权；分析使用配置的 LLM，可单独选择模型、限制成本，
  开启会话分析意味着同意向该模型发送该白名单会话内容，默认关闭会话分析。
- 长输入有界分片，完整覆盖后发布；摘要长度受限，事实有证据；失败不得伪造空摘要成功。
- 配置、聊天正文、模型密钥、真实数据不进入 Git 或普通日志。

## 本轮结果

### 后端落点

- `app/domains/message_history.py`：协议、SQLite 历史/策略/批次/信息点、证据与权限校验。
- `app/core/message_analysis.py`：独立后台分析，固定范围分片、预算、撤销/租约 fencing；
  使用现有 LLM 服务，不依赖个人记忆开关。`input_chunk_bytes` 只限制原消息数组，
  有界旧摘要/事实另计，完整请求仍受模型容量与总 token 预算约束。
- `app/api/routes/messages.py`：本地管理/读取与独立凭据导入，合同见 `api_contract.md`。
- `app/tool_packages/messages.py`：Agent 只读查询，不向 Agent 提供采集或分析写入口。
- `app/core/background_jobs.py`：共享队列按已注册 kind 领取，防止不同领域 worker 抢错任务。

### 前端落点与收口

前端仓库为 `/mnt/d/agent-bot-frontend`，沿用现有页面和样式，不另建 React 项目。

- `app/plugins/qq_reader.py` / `message_sources.py`：QQ 与注入的 Mock 共用接收/白名单/
  outbox 路径；旧消息表不动。新队列仅按当前策略 revision 同步，旧版本未确认行隔离。
- `app/web/pet/message-history.js` 及原 QQ 插件面板：白名单编辑、记录/分析独立开关、
  时间/发言者/序号、历史翻页、摘要覆盖、事实来源、尾批处理与版本化失败重试。
- Java bridge 只扩大消息历史管理/查询的精确路径白名单，不开放消息导入或 OneBot API。
- 采集待发送队列达到 10,000 条时暂停读取，不静默删除旧历史。队列上限并非全部历史
  文件大小上限；已同步/隔离数据保留。离线缓存无法即时获知撤销，刷新策略才生效。
  QQ/OneBot 不保证补拉，连接断开或队列满期间不承诺完整捕获。
- 前端操作说明见该仓库 `docs/message_history_frontend.md`。

### 启用方式（不修改现有私有配置）

1. 后端设置 `LKA_MESSAGES_IMPORT_TOKEN`；前端本地服务的 `QQ_SYNC_TOKEN` 设置为同一值。
   它与 `QQ_WS_TOKEN` 必须不同，不把采集凭据填入浏览器管理令牌框。
2. 前端 `QQ_SYNC_URL=http://127.0.0.1:8765/integrations/messages/import`，沿用 QQ Reader 的
   `QQ_READER_ENABLED`、仅 loopback 的 `QQ_WS_URL`、账号校验和私有本地数据库配置。
   两端必须处于能互相访问 loopback 的环境；这里未放宽为局域网或公网。
3. 在前端消息历史面板手动添加 platform/account/conversation 白名单；先只开“记录”。
   后端可额外设置 `LKA_MESSAGES_API_TOKEN`，该值仅用于管理面板，页面内存保存。
4. 确认模型配置及内容外发边界后，再为该会话打开“分析”，设置批量（默认 20）。
   可在 `[message_history]` 独立指定已配置的 client/model；也可只记录、不调用模型。
5. 打开 Agent 的 `messages` 工具包即可读取启用会话的历史、摘要和信息点；不足一批的
   原文不丢失，摘要同时返回覆盖水位及有限未处理尾部，完整内容用 history 分页。
