# 消息整理阻塞恢复与积压回放

## 目标与边界

2026-10-06 实机发现三个启用群的下一批任务均失败；扫描和采集仍运行，但失败任务
占据连续水位的下一段。当前小时无调用、滚动日用量 136652/200000 token，非当前配额耗尽。
旧错误分类把检查点变化与模型校验失败一起记为 `model_output_invalid`。

只修复后台阻塞、可控积压回放并部署 Windows；消息正文交付、摘要展示和规则误报另行处理。
不删除原始消息、不改变许可或 cutover、不跳过失败范围、不清零账本、不自动增加配额。

## 实施与实机结果

工程改动：`message_analysis.py` 冻结历史事实、区分异常、生成 <=480 UTF-8 字节的
schema-owned 校验反馈，分片为恢复反馈预留512计数单位；不复制坏输出或注入场景关键词。
`message_reading_runtime.py` 原地重建并归档检查点、持久化回放目标；
`messages.py` 增加管理 API 与状态；通用后台 worker 只认识有界错误代码，不认识消息领域。

最终针对性回归 **120 passed / 34.53s**：恢复、production v3、调度、控制、legacy
执行、分析、消息 API、共享后台队列。新增恢复测试覆盖未知成员 ID 仍拒绝、代表消息
只补全已见成员关系、明确增加工作额度才授予额外重建，额度不变不授予。
本轮相关文件 Ruff、`git diff --check` 通过。
隔离环境 socketpair 唤醒受限会挂起 asyncio，切换宿主环境后离线测试正常完成；不是
修改产品代码去规避测试。真实消息仅保存在本地数据/日志，不复制到本文件。

持续无效输出或累计工作预算耗尽仍明确阻塞，不能靠
无限重试、忽略证据校验或自动增加额度伪装完成；状态可区分该阻塞与滚动配额等待。
